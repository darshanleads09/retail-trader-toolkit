# Introduction

![Status: In progress](https://img.shields.io/badge/status-In%20progress-yellow)

This plan describes the end-to-end implementation of **ScalpMaster Pro** — an autonomous, event-driven AI agent that replicates the 8-indicator scoring logic of the TradingView *AI-Powered ScalpMaster Pro* indicator and executes NIFTY/BANKNIFTY options scalp trades on Zerodha via Kite Connect v3. The system is built on Google Cloud (ADK, Gemini 3.5 Flash/Pro, Pub/Sub, Cloud Run, Firestore, Cloud Scheduler, Secret Manager) and submitted to the **All Things Agentic Hackathon** under the **Taskmaster** track.

**Version 2.0** upgrades the risk and execution layer to institutional-grade quantitative standards, authored from the perspective of a CMT, CQF holder, and Senior Hedge Fund Manager with 15+ years of systematic trading experience. The agent now incorporates: **Kelly Criterion** optimal position sizing, **GARCH(1,1)** intraday volatility forecasting, **ATR-14 dynamic stop-loss** calibration, **Expected Value (EV) gating** per trade, **IV Percentile filtering** to avoid overpaying for premium, and **regime-conditional signal thresholds** that tighten entry criteria in volatile or low-liquidity regimes.

The agent operates fully autonomously during NSE market hours (09:15–15:15 IST), requires zero human intervention per trade, and persists a self-improving strategy memory across sessions.

## 1. Requirements & Constraints

- **REQ-001**: The system must replicate all 8 ScalpMaster Pro indicators: RSI-14, MACD(12,26,9), Stochastic-%K, Momentum-10, EMA-200, SuperTrend(ATR), CCI-20, OBV-ROC — each returning a discrete `bull` or `bear` signal per evaluation cycle.
- **REQ-002**: A STRONG BUY signal requires `bull_score >= 6 AND bull_score > bear_score AND ema_zone == "UP"`. A STRONG SELL signal requires `bear_score >= 6 AND bear_score > bull_score AND ema_zone == "DOWN"`.
- **REQ-003**: Default risk/reward ratio must be 1:2 — Stop Loss at 1% from entry, Take Profit at 2% from entry. When ATR-based SL (REQ-011) is active, the fixed 1% SL is superseded.
- **REQ-004**: All trades must use Zerodha product type `MIS` (intraday margin). All open MIS positions must be force-closed by 15:15 IST daily.
- **REQ-005**: The Gemini 3.5 Decision Agent must return a structured JSON response containing fields: `action` (EXECUTE|SKIP|WAIT), `confidence` (FULL_CONFIDENCE|LOW_CONFIDENCE), `reasoning` (string, max 3 sentences), `entry_price` (float), `tp_price` (float), `sl_price` (float).
- **REQ-006**: The Reflection Agent must run after every closed trade and write an updated `strategy_memory/{YYYY-MM-DD}` document to Firestore within 30 seconds of trade closure.
- **REQ-007**: The system must support both NIFTY (lot size 50) and BANKNIFTY (lot size 15) option chains on the NFO segment.
- **REQ-008**: The instrument token list must be refreshed daily at 08:00 IST from `kite.instruments("NFO")`, filtering for weekly expiry CE and PE contracts within ±500 points of spot for NIFTY and ±1000 points for BANKNIFTY.
- **REQ-009**: The Kite Connect `access_token` must be renewed daily before 09:00 IST and stored in Google Secret Manager under secret ID `kite-access-token`.
- **REQ-010**: The agent must publish a Pub/Sub message to topic `scalpmaster-ticks` for every WebSocket tick received from KiteTicker in `MODE_FULL`.
- **REQ-011**: The Quant Risk Layer must compute ATR-14 on the underlying spot (NIFTY/BANKNIFTY) at signal time and set dynamic SL = `entry_price - (1.5 × ATR_14)` for BUY trades and `entry_price + (1.5 × ATR_14)` for SELL trades. TP must be set at `entry_price ± (3.0 × ATR_14)` to maintain minimum 1:2 RR. If ATR-based SL exceeds 2% of entry price, the trade must be blocked by the Risk Guard Agent.
- **REQ-012**: The Quant Risk Layer must compute a **Kelly Criterion** optimal position size before every trade execution. Formula: `f* = (W × R - (1 - W)) / R` where `W` = rolling 20-trade win rate from Firestore `trades` collection, `R` = average win/loss ratio from same 20 trades. Apply a **half-Kelly** fraction (`0.5 × f*`) as the position size as a percentage of available capital. Minimum position: 1 lot. Maximum position: 5 lots (hard cap per REQ-004 capital constraint).
- **REQ-013**: The Quant Risk Layer must fit a **GARCH(1,1)** model on the last 100 one-minute close returns of the underlying spot instrument at signal time. The one-step-ahead conditional volatility forecast (`σ_t+1`) must be used to: (a) scale the ATR-based SL by `max(1.0, σ_t+1 / σ_historical_mean)` when forecast volatility exceeds the 30-day mean; (b) reduce Kelly position size by 50% when `σ_t+1 > 2 × σ_historical_mean`.
- **REQ-014**: The Decision Agent must compute and log the **Expected Value (EV)** of each trade before execution: `EV = (W × TP_distance) - ((1 - W) × SL_distance)` where distances are in absolute price terms. Trades with `EV <= 0` must be blocked regardless of bull/bear score. EV must be stored in the `TradeRecord` Firestore document.
- **REQ-015**: The system must apply an **IV Percentile filter**: compute the current IV of the target option as a percentile rank against the last 30 trading days of IV data stored in Firestore `iv_history/{symbol}`. Block trade entry if `IV_percentile > 80` for long option trades (buying overpriced premium). Log the IV percentile in the `TradeRecord`.
- **SEC-001**: The Kite `api_key` and `api_secret` must be stored exclusively in Google Secret Manager. They must never appear in source code, environment variables, or Firestore documents.
- **SEC-002**: All Cloud Run service endpoints must require authentication (IAM-based). No public unauthenticated access is permitted.
- **SEC-003**: Firestore security rules must restrict read/write to the Cloud Run service account identity only.
- **SEC-004**: The Risk Guard Agent must enforce hard-block rules that cannot be overridden by Gemini output under any circumstances.
- **CON-001**: Kite Connect REST API rate limit is 3 requests/second. All REST calls must be throttled using a token-bucket rate limiter with capacity=3, refill_rate=3/sec.
- **CON-002**: KiteTicker WebSocket supports a maximum of 3000 instrument subscriptions per connection. Subscriptions must not exceed 200 instruments per session to stay within budget.
- **CON-003**: The `access_token` expires daily at midnight IST. The re-auth Cloud Scheduler job must complete before 09:00 IST.
- **CON-004**: Cloud Run minimum instances must be set to 0 outside market hours (15:30–08:45 IST) to eliminate idle billing.
- **CON-005**: Gemini Pro must only be invoked for the Reflection Agent post-trade analysis. All real-time Decision Agent calls must use Gemini 3.5 Flash to minimize latency and cost.
- **CON-006**: The total GCP spend must not exceed the $150 hackathon credit allocation. Budget alerts must be configured at $75 (50%) and $120 (80%) thresholds.
- **CON-007**: GARCH(1,1) model fitting must complete within 500ms. Use `arch` library with `scipy` BFGS optimizer. If fitting exceeds 500ms timeout, fall back to realized volatility (rolling 20-bar standard deviation of returns × √252 × √(1/375)) and log the fallback event to Firestore `system_logs`.
- **CON-008**: Kelly Criterion calculation requires a minimum of 10 completed trades in Firestore `trades` collection. If fewer than 10 trades exist, default to a fixed position size of 1 lot and log `kelly_fallback: true` in the `TradeRecord`.
- **GUD-001**: All agent modules must be independently deployable Python packages under `src/agents/`. No agent module may import from another agent module directly — communication occurs exclusively via Pub/Sub messages or Firestore reads.
- **GUD-002**: All Firestore writes must use server-side timestamps (`firestore.SERVER_TIMESTAMP`) for `created_at` and `updated_at` fields.
- **GUD-003**: All Gemini prompts must be stored as versioned string constants in `src/prompts/prompts.py`, not inline in agent code.
- **GUD-004**: Every trade execution attempt must be logged to Firestore collection `execution_log/{order_id}` regardless of success or failure, including the full Kite API response or exception message.
- **GUD-005**: All quantitative model outputs (Kelly fraction, GARCH σ_t+1, EV, IV percentile, ATR-14) must be stored in the `TradeRecord` Firestore document under a nested field `quant_metrics: dict` for auditability and Reflection Agent consumption.
- **GUD-006**: Regime-conditional signal thresholds must be enforced: in `volatile` regime, require `bull_score >= 7` (not 6) for STRONG BUY/SELL; in `ranging` regime, skip all trades regardless of score (statistical edge collapses in mean-reverting, low-ATR environments for directional options).
- **PAT-001**: Follow the ADK Sequential Agent pattern for the main trade pipeline: Signal Agent → Decision Agent → Risk Guard Agent → **Quant Risk Agent** → Execution Agent → Monitor Agent → Reflection Agent.
- **PAT-002**: Use the ADK Parallel Agent pattern within the Signal Agent to compute all 8 indicator scores concurrently using `asyncio.gather()`.
- **PAT-003**: Use Firestore as the single source of truth for all agent state. No in-memory state may persist across Cloud Run request boundaries.
- **PAT-004**: The Quant Risk Agent must run as a **gate** between Risk Guard and Execution: it computes Kelly size, GARCH forecast, EV, and IV percentile, then either enriches the `DecisionOutput` with `quantity` and updated `sl_price`/`tp_price`, or returns a `BLOCKED` status with quantitative justification.
- **PAT-005**: IV history must be maintained as a **rolling append-only log** in Firestore `iv_history/{symbol}/{date}` with field `iv: float`, written by the Signal Agent on every evaluation cycle. The IV Percentile filter reads the last 30 documents ordered by `date desc`.

## 3. Alternatives

- **ALT-001**: Use Alpaca or Interactive Brokers API instead of Kite Connect v3 — rejected because the project is specifically designed for NIFTY/BANKNIFTY on NSE/NFO, and Kite Connect is the most reliable, lowest-latency broker API for Indian markets with native WebSocket tick streaming.
- **ALT-002**: Use a rule-based engine (pure `if/else` on `bull_score >= 6`) instead of Gemini 3.5 for the Decision Agent — rejected because it eliminates the agentic reasoning layer that differentiates this project from a simple trading bot and is required to score on the Innovation criterion (40%).
- **ALT-003**: Use Redis instead of Firestore for agent state — rejected because Firestore is serverless, scales to zero, has native GCP IAM integration, and eliminates the need for a dedicated always-on cache cluster (violates CON-004 and CON-006).
- **ALT-004**: Use LangChain instead of Google ADK — rejected because the hackathon explicitly recommends ADK and judges will evaluate use of Google-native tooling. ADK also provides native Vertex AI integration with lower boilerplate.
- **ALT-005**: Use `ta-lib` instead of `pandas-ta` for indicator computation — rejected because `ta-lib` requires a C library system dependency that complicates Docker builds. `pandas-ta` is pure Python and pip-installable without system dependencies.
- **ALT-006**: Deploy on GKE instead of Cloud Run — rejected because Cloud Run scales to zero (CON-004), requires no cluster management, and is sufficient for the agent's request-driven workload pattern.
- **ALT-007**: Use fixed fractional position sizing (e.g., always 2% of capital per trade) instead of Kelly Criterion — rejected because fixed fractional sizing ignores the empirical win rate and payoff ratio of the specific strategy, producing suboptimal geometric growth. Kelly Criterion maximizes long-run capital growth given the strategy's observed edge, which is the institutional standard for systematic funds.
- **ALT-008**: Use EWMA (RiskMetrics) volatility instead of GARCH(1,1) — considered as a simpler alternative. EWMA with λ=0.94 is computationally cheaper but does not model volatility clustering (the ARCH effect) that is empirically significant in NIFTY intraday returns. GARCH(1,1) provides superior one-step-ahead forecasts for options scalping where volatility regime shifts within a session. EWMA retained as the CON-007 fallback only.
